Before code

Useful software starts before the ticket exists.

The value I want the site to prove is problem formation: learning a domain, finding the constraint that matters, and building the smallest artifact that makes the next decision obvious.

01

Messy input

Vague goals, half-known workflows, contradictory requests, domain language, edge cases, and the constraint nobody mentions until it breaks something.

02

Model

I turn that into actors, data, states, trade-offs, interfaces, and a clear first version someone can argue with before too much code exists.

03

Working proof

The first artifact should answer a real question: does this workflow help, does this score make sense, does this interface make action easier?

I do not just write the code after the problem is defined. I help define the problem well enough that the code has somewhere meaningful to go.

Case files

Projects where the problem mattered as much as the code.

Four projects from the last three years. Different domains, different stacks — the common thread is figuring out what the actual problem was before writing any code.

Healthcare · 2025 — in progress Python · DuckDB

Tuya Analytics

A primary-care clinic needed a weekly list of the patients most at-risk of falling through the cracks — and a way to justify every name on it to clinicians.

A local Python + DuckDB tool that ingests Practice Fusion Bulk FHIR exports and weekly appointment reports, then runs a configurable rubric scoring engine over the patient panel. Versioned runs, component-level audit trails, and a CLI that can diff a new scoring rubric against the previous one before it ever touches the UI.

  • FHIR Bulk ingest into a single-file DuckDB warehouse
  • YAML-driven rubric with per-component score explanations
  • v1/v2 engines run in parallel for safe migrations
  • All local — PHI never leaves the laptop

The clinic gets a defensible worklist every Monday morning.

LLM systems · 2023 Capstone

Gompai github / capstone

Senior CS capstone: an AI chatbot robot with visual recognition and per-person memory. The interesting problem wasn't the hardware — it was designing the brain.

We split the agent into two cooperating models — a fast one for reactive speech and a slower one for deliberation — and built a semantic-meaning memory store that the slow model retrieved from before generating. Patterns that are standard in production LLM stacks today; in 2023 we were sketching them from first principles.

  • Dual-model brain: reactive speech & slower thought
  • Embedding-based memory + retrieval before generation
  • Computer-vision module for face / person recognition
  • Persistent identity for the robot across conversations

The first time I had to design a system before the off-the-shelf abstractions for it existed.

Healthcare · 2025 EN / ES · hand-written

Tuya PA tuyamedical.com

The clinic's front desk was fielding constant calls for things that should have been on the website — hours, addresses, intake forms, what insurance they accept. The old BootstrapMade site wasn't helping.

Full rewrite into hand-written HTML and CSS, no build step and no dependencies. Bilingual EN/ES mirror with proper hreflang, a Patient Fusion OAuth callback, public JWKS, downloadable PDFs, and a sitemap. The whole site fits in one folder a non-engineer could edit.

  • Zero npm dependencies, zero build step
  • OAuth callback + JWKS for clinical integrations
  • Properly localized alternates and JSON-LD per language

Patients self-serve hours, locations, and forms — fewer calls for the front desk.

Hospitality · 2025 EN / ES / PT · Astro 5

Taxi Wine Mendoza, AR

A single-driver private wine tour needed a credible web presence that worked in three languages and routed serious inquiries straight to a phone — without paying a booking platform a cut of every trip.

A trilingual marketing site in Astro 5 + Tailwind v4. One typed config file drives services, routes, FAQs, and the per-language JSON-LD. A floating WhatsApp action turns interest into an actual conversation in one tap.

  • Three localized routes with proper hreflang alternates
  • Single site.config.ts owns 99% of the content
  • No third-party booking widget, no platform fees

Visitors land in their own language and book a tour directly with the driver.

Engineering principles

The edge is knowing what the system should be.

Plenty of people can write code once the shape is obvious. I like the stranger part: turning human context into a design that can be tested, built, and maintained.

  1. 01

    Ambiguity is signal

    A vague request is not a failure state. It is raw material. The first job is extracting actors, incentives, constraints, and failure modes from the fog.

  2. 02

    Translate before deciding

    I move between human language and machine logic until the idea has a testable shape: data, states, interfaces, risks, and trade-offs someone can argue with.

  3. 03

    Prototype the hard truth

    The first build should answer the riskiest question, not decorate the safest one. A small working system teaches faster than a huge speculative plan.

  4. 04

    Make the machine explain itself

    A system should reveal its assumptions: why this score, why this recommendation, why this workflow. If it cannot be explained, it cannot be trusted.

About
